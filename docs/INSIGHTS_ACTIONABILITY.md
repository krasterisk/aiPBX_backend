# C4.17 — полезные рекомендации супервизору

Координатор: /root. Режим: codex-direct, без субагентов. Baseline: backend 4daa827 / 2.9.32, frontend 1d273f5b / 3.7.31. Статус: implemented / automated-tests-passed; live-provider проверен только на синтетике. Не released, выпуск не назначен.

## Требование и план

Низкая оценка сама по себе не является выводом. Карточка должна содержать подтверждённое наблюдение в разговорах, конкретное изменение поведения или проверку применимости критерия и способ проверить результат. Причинность, финансовый эффект и распространённость причины нельзя выводить из среднего балла или небольшого набора примеров.

Дополнение пользователя: инструкции универсальны для разных видов деятельности. В рабочих промптах нет клинического сценария по умолчанию. Название, описание и текущие инструкции выбранного проекта задают контекст; frozen instruction/businessContext каждого разговора задают историческое правило. Советы сотруднику отличаются от изменения сценария бота, если тип исполнителя явно известен. Речь не доказывает невидимую операцию в CRM. Неизвестный предмет вопроса не подтверждает применимость или исключение. Никакие настройки проекта «Панацея» в рамках этой задачи не меняются.

1. Сохранить серверные числа, фильтры, сравнение совместимых периодов и tenant scope. Загрузить ограниченные примеры только текущих разборов и выбранных критериев; передать правила, темы и текст разговоров без телефонов/почты.
2. Вместо выбора шаблона разрешить структурированный вывод, конкретное действие и проверку. Потребовать дословные цитаты из существующих примеров. Неизвестная применимость → отказ; документированное противоречие явному исключению → проверка критерия, а не требование увеличить продажи.
3. Валидировать идентификаторы, цитаты поведения и условий применимости, структуру, границы численных заявлений и минимальное число независимых примеров. Невалидные ответы проходят существующий retry/fallback с фиксированным исправляющим сообщением без цитирования отклонённого ответа. Затем отдельный фактчек Pro проверяет наблюдение, уместность предложения и измеримость проверки. Неподтверждённые планы не заменяются общими советами. Допустим пустой результат.
4. Сменить версию кеша и включить доказательства в digest. Сохранить совместимость UI: вывод в observation, действие и проверка в recommendation, ссылки — на использованные звонки.
5. Проверить регрессии unit/service, реальный локальный PostgreSQL и DeepSeek Pro на синтетических разговорах. Различать автотесты, модельную квалификацию и production.

Owned: operator-analytics.service.ts (только verified-insights), lib/verified-insights.ts и тесты, lib/insight-evidence.ts, новые lib/insight-call-evidence.ts, lib/actionable-insights.ts и их тесты, verified-insights.service.spec.ts, test/fixtures/actionable-insights.cases.cjs, OPERATOR_ANALYTICS_ENV.md, этот документ. Формула/получатель списания, scoring, разборы Flash, конфигурации/данные production, фронтенд и workflow не меняются; в usage успешного запроса учитываются генерация и фактчек. Без карточек на первой стадии фактчек не вызывается. Старые dirty tsbuildinfo/__pycache__ сохраняются. Ключи и реальные разговоры в Git не сохраняются.

## Приёмка

Нет результата из одного среднего балла; нет шаблонного fallback. Доказательства только из текущего scoped run; ссылки и цитаты проверены. Изменение, ответственный, следующая выборка и критерий проверки обязательны. При неизвестной применимости нет команды предлагать услуги всем клиентам. Числа и сравнения остаются серверными; модель не обещает выручку/рост. Пустой ответ допустим. Кеш старого формата не используется. Модель инсайтов Pro, разборов Flash.

Синтетический корпус: клиника как регрессия, интернет-магазин, техподдержка, доставка, бухгалтерские услуги, обучение, автоматический ассистент, невидимые операции CRM. Нужны положительные конкретные планы в известных ситуациях и отказ при неизвестной цели/политике/невидимом действии; не просто валидный JSON. Проверки отслеживают чужую отраслевую лексику и неподтверждённые предложения. Для повреждённого контекста с prompt injection безопасный пустой результат допустим: не заставляем модель давать совет из скомпрометированных инструкций.

Первый межотраслевой прогон выявил необоснованное исключение неопределённого запроса из оценки. Уточнены оба промпта: отсутствие упоминания условия не доказывает его отсутствия. Итоговый live-прогон по прежнему строгому gold для injection записал 18/19; финальная квалификация по исправленному критерию безопасности принимает пустой ответ в этом кейсе. Входы/ответы модели при replay не менялись. Поправлен также семантический matcher, ранее не принимавший корректное «перевести компетентному сотруднику» как передачу вопроса. Предыдущие неуспешные результаты сохранены, а не перезаписаны как успешные.

Пример итогового плана для доставки: в обоих полных разговорах вопрос остаётся нерешённым, а оператор не сообщает ответственного и способ связи. Действие — после обещания передать вопрос назвать ответственного по регламенту и согласовать канал связи; проверка — отмечать эти два шага в следующих сопоставимых обращениях. Выдумывать дату доставки или название отдела запрещено. Это пример из синтетики, а не найденная проблема реального клиента.
