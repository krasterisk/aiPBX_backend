# Operator Analytics — переменные окружения

Ниже приведены значения и дефолты переменных аналитики. Рабочие ключи провайдеров хранятся только в закрытом серверном окружении.

> **Принцип BC:** все поведенческие флаги имеют безопасный дефолт (выключено / legacy). Прод-поведение не меняется, пока флаг не включён явно. Пороговые переменные опциональны — при отсутствии берётся дефолт из кода (`DEFAULT_TRANSCRIPTION_QUALITY_THRESHOLDS`).

## STT / LLM провайдеры

При `ANALYTICS_DEEPSEEK_ENABLED=true` и заданном `ANALYTICS_DEEPSEEK_API_KEY` разборы звонков используют цепочку **DeepSeek Flash (`deepseek-flash`) → OpenAI → Ollama**, а инсайты — **DeepSeek V4 Pro (`deepseek-v4-pro`) → те же резервы**. Модель инсайтов задаётся отдельно: `ANALYTICS_INSIGHTS_DEEPSEEK_MODEL=deepseek-v4-pro`. Этот параметр не меняет модель разбора, проверки тем или метрик. Без включения DeepSeek сохраняется порядок OpenAI → Ollama. Для резервов задайте `ANALYTICS_LLM_MODEL=gpt-5-nano` и `ANALYTICS_FALLBACK_MODEL=qwen3.5:9b`.

Параметр модели читается при запуске backend. После изменения env существующий процесс сохраняет прежнюю настройку до следующего запуска/выпуска. Для production с Docker Compose параметр хранится в `/app/.env.production` и должен входить в окружение сервиса backend. Кеш legacy и quality-preview инсайтов учитывает выбранную модель; ответы другой модели не переиспользуются.

DeepSeek вызывается с отключённым thinking и потоковым JSON-ответом: до15с до первого содержательного фрагмента, до15с без новых данных, до60с на всю попытку. Заголовки HTTP, keepalive и пустые SSE-фрагменты не считаются прогрессом. При временных ошибках — максимум3попытки с паузами5и15с; SDK-повторы отключены. HTTP400/401/402/403/404/422 сразу переводят запрос следующему провайдеру. Обрыв, усечение, некорректный JSON или нарушение полной схемы анализа также не принимаются за успешный ответ. Семантическую правильность темы по одному JSON-формату установить невозможно; квалификация промптов проверяется отдельным набором примеров.

При трёх ожиданиях первого фрагмента переход на OpenAI занимает примерно65с (3×15+5+15). При трёх полных60-секундных попытках — до200с. OpenAI имеет отдельный90-секундный предел и одну попытку; Ollama —120с и одну попытку, native `/api/chat` с `think=false`. Дальнейший неуспех возвращается как ошибка аналитики без фиктивного успешного результата. Сохраняются модель и usage фактически принятого ответа. В логах отказов — только провайдер, модель, номер попытки и категория ошибки, без тела ответа, транскрипта или ключей.

| Переменная | Дефолт | Назначение |
|---|---|---|
| `DEFAULT_STT_PROVIDER` | `whisper` | Провайдер распознавания речи по умолчанию (`whisper` / внешний). |
| `DEFAULT_OLLAMA_MODEL` | `gemma4:e4b` | Локальная LLM-модель для анализа (Ollama). |
| `ANALYTICS_FALLBACK_MODEL` | `gemma4:e4b` | Фолбэк-модель, если основной LLM-путь недоступен. |
| `OPERATOR_ANALYTICS_ALLOW_INSECURE_SSL` | `true` | Скачивать записи по HTTPS с self-signed сертификатами (`analyze-url` / regenerate). `false` — строгая проверка TLS. |

## Контроль качества распознавания (anti-garbage, §6)

Двухслойный гейт: сигналы STT до вызова LLM + самооценка LLM. Итоговый вердикт — худшая из severities. Записи с `unusable` не доходят до LLM (нет списания LLM), `low` анализируются с пометкой.

| Переменная | Дефолт | Назначение |
|---|---|---|
| `OPERATOR_ANALYSIS_MIN_DURATION_SEC` | `10` | Минимальная длительность записи (сек). Короче → `ERROR` без списания LLM. |
| `OPERATOR_QUALITY_MIN_WORDS` | `15` | Минимум слов в транскрипте; меньше → `unusable`. Отсекает «аналитику по нескольким словам». |
| `OPERATOR_QUALITY_AVG_LOGPROB_MIN` | `-1.0` | Порог среднего `avg_logprob` STT: ниже → `low`. |
| `OPERATOR_QUALITY_AVG_LOGPROB_UNUSABLE` | `-1.3` | Ниже → вклад в `unusable` (модель не уверена в распознанном). |
| `OPERATOR_QUALITY_MAX_NOSPEECH` | `0.6` | Доля «нет речи» (`no_speech_prob`): выше → `low`. |
| `OPERATOR_QUALITY_MAX_NOSPEECH_UNUSABLE` | `0.8` | Выше → `unusable` (тишина/шум). |
| `OPERATOR_QUALITY_MAX_COMPRESSION` | `2.4` | Compression ratio выше → `low` (повтор/галлюцинация). |
| `OPERATOR_QUALITY_MIN_COMPRESSION` | `0.5` | Compression ratio ниже → `low` (слишком разреженно). |
| `OPERATOR_QUALITY_MIN_LANGUAGE_PROB` | `0.5` | Уверенность определения языка ниже → `low`. |

## AI Insights (dashboard)

| Переменная | Дефолт | Назначение |
|---|---|---|
| `ANALYTICS_INSIGHTS_DEEPSEEK_MODEL` | `deepseek-v4-pro` | Отдельная DeepSeek-модель только для инсайтов (legacy и quality-preview). Пустое значение использует дефолт; пробелы по краям удаляются. Разбор звонков сохраняет `deepseek-flash`. |
| `OPERATOR_INSIGHTS_MIN_CALLS` | `10` | Минимум проанализированных звонков для генерации инсайтов (и флаг `insightsAvailable` на дашборде). |
| `OPERATOR_INSIGHTS_TTL_SEC` | `3600` | TTL in-memory кэша инсайтов (секунды). |
| `OPERATOR_INSIGHTS_MAX_COUNT` | `6` | Максимум инсайтов в ответе API. |

Ключ кэша включает `userId` (tenant), фильтры, `INSIGHTS_PROMPT_VERSION` и digest фактов. Query `refresh=1` обходит кэш.

Для нового дашборда quality-preview используется отдельная версия `verified-insights-2-actionable`. Низкие баллы остаются кандидатами для проверки, а не готовыми карточками. Модель получает определения критериев и ограниченный набор полных разговоров из той же выборки и текущих immutable run: до двух текущих примеров и одного предыдущего на критерий, до восьми кандидатов. Телефоны и почта маскируются; внутренние channelId не передаются модели. Длинные обрезанные разговоры не используются для доказательства пропуска действия. Критерии с различающимися историческими определениями/контекстом между периодами не сравниваются.

Инсайт обязан содержать наблюдение, применимость, конкретное действие, проверку следующей сопоставимой выборки, наблюдаемый признак результата и ограничение. Отрасль не задана по умолчанию: передаются название, описание и инструкции выбранного проекта, а в каждом примере — frozen businessContext и определение критерия. Отдельно различаются изменение работы сотрудника/сценария бота, неверная применимость критерия, противоречие сохранённой оценки тексту и воспроизводимая удачная практика. Речь не доказывает невидимые операции во внешних системах; неизвестная цель не даёт основания объявлять критерий неприменимым. Сервер проверяет factId, дословность цитат, независимость текущих примеров, наличие предыдущих оснований для тренда, структуру ответа и отсутствие произвольных численных заявлений в сгенерированном тексте. Числа/знаменатели/сравнения сохраняются серверными. Семантическую верность причин и советов одна структурная проверка не доказывает: промпт ограничивает вывод проверенными примерами, а модель отдельно квалифицируется на противоречивых синтетических кейсах разных видов деятельности.

Контракт JSON продублирован в системном сообщении: DeepSeek использует JSON object mode и не получает OpenAI JSON Schema как отдельное ограничение. Сообщение каждой стадии содержит слово JSON и пример ([контракт API](https://api-docs.deepseek.com/guides/json_mode/)). `validateContent` подключён к существующей цепочке retry/fallback; при структурном отказе добавляется фиксированная подсказка, без отражения непроверенного ответа модели. Невалидный ответ не превращается в стандартное «разобрать звонки»: после отказа провайдеров возвращается ошибка. Без необходимых разговоров запрос к модели не выполняется; допустим результат без карточек.

После генерации непустого плана выполняется отдельный фактчек Pro: для каждого факта проверяются подтверждение наблюдения, уместность предложенного действия и наблюдаемость проверки. Он может только принять/отклонить уже проверенные карточки, не создавать новые факты или советы. Предложения будущих действий отличаются от утверждений о прошлом; для полезного изменения не требуется, чтобы оно уже выполнялось в проблемном разговоре. Неподтверждённые коммерческие обещания блокируются также сервером. Ставка и получатель списания прежние; usage успешной генерации включает оба принятых ответа. Если первая стадия вернула пустой результат, фактчек не вызывается.

Кеш учитывает содержимое доказательств, immutable run, контекст, аудиторию, модель и хеш обоих промптов, но не меняет ключ лишь от продвижения часов при неизменной выборке. Новых env-параметров и изменений модели Flash для разбора нет. План и evidence: [INSIGHTS_ACTIONABILITY](INSIGHTS_ACTIONABILITY.md).

| Переменная | Дефолт | Назначение |
|---|---|---|
| `OPERATOR_EVIDENCE_MAX_CALLS` | `300` | Максимум звонков, загружаемых для агрегации evidence в панели оператора (`GET /operator-analytics/operator-evidence`). Ограничивает latency и объём цитат в ответе; клиентский `limit` может только уменьшить cap. Per-metric evidence дополнительно ограничен 5 элементами на метрику в коде. Оба порога стоит пересмотреть на UAT. |

### Troubleshooting: insight billing FK error

Инсайты и генерация промптов пишут `billingRecords` с синтетическим `channelId` (`insight-*`, `prompt-*`), без строки в `aiCdr`. На старых БД остаётся FK `billingRecords.channelId → aiCdr.channelId` и INSERT падает с `ER_NO_REFERENCED_ROW_2`.

**Исправление (MySQL):** применить миграцию  
`migrations/mysql/2026-03-15-billing-records-add-userId-description.sql`  
(она снимает FK на `channelId` и добавляет `userId` / `description`).

Быстрая проверка:

```sql
ALTER TABLE `billingRecords` DROP FOREIGN KEY `billingRecords_ibfk_1`;
```

(имя ограничения может отличаться — миграция ищет его по `information_schema`.)

## Пайплайн (§13)

| Переменная | Дефолт | Назначение |
|---|---|---|
| `OPERATOR_STUCK_MINUTES` | `0` | Reaper: записи в `processing` старше N минут → `ERROR` («timeout»), без доп. списаний. `0` → выключено. Cron каждые 10 мин. |
| `OPERATOR_DEDUP_BY_HASH` | `false` | Дедуп загрузок: одинаковый SHA-256 аудио + тот же `projectId` → переиспользовать готовый анализ, без STT/LLM/списания. |

Дедуп требует колонку `audioSha256` (миграция `2026-06-18-operator-audio-hash`). Дашборд агрегирует числовые метрики через `operator_metric_values` (SQL `GROUP BY`) с fallback на JSON; time series / scorecards — постраничная загрузка CDR.
